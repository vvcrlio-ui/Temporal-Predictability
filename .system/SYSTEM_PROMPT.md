# Specification-Driven Development Methodology

## Purpose

本文档描述本项目采用的、可跨 AI 工具复用的规范驱动开发（SDD）方法论。

它不承担工具自动发现职责，也不重复维护仓库级硬约束。各工具的入口文件必须显式要求读取本文档：

- Codex：`AGENTS.md`
- Claude Code：`CLAUDE.md`

仓库边界、指令优先级和强制工作流以 `AGENTS.md` 为准；本文档解释如何高质量地执行该工作流。

## SDD Information Model

项目事实按职责分离：

| 文档 | 唯一职责 |
|---|---|
| `.system/CONTEXT_MAP.md` | 提供项目入口、当前焦点和文档导航 |
| `ARCHITECTURE.md` | 保存长期稳定的边界、依赖规则、业务不变量和技术决策 |
| `ROADMAP.md` | 保存任务状态、范围、非目标、依赖和验收标准 |
| `TESTS.md` | 保存质量门槛、测试矩阵、标准命令和验证基线 |
| `LESSONS.md` | 保存尚未被正式规范覆盖的跨任务工程经验 |
| `plans/` | 保存特定工作包的详细研究或实现设计附件 |

同一事实只在一个权威文档中维护。索引可以引用事实，但不复制其完整内容；详细计划不得悄然覆盖 `ARCHITECTURE.md` 或 `ROADMAP.md`。

## 1. Frame the Task

开始实施前，把用户请求转化为一个可验证的问题陈述：

- 目标行为是什么？
- 当前行为或状态是什么？
- 修改范围和明确非目标是什么？
- 哪些架构边界、数据契约或研究不变量适用？
- 什么证据可以证明任务完成？
- 哪些风险可能使表面通过的结果仍然无效？

对调查或解释任务，目标证据可以是代码、配置、日志或可复现命令；对实现任务，目标证据还应包括测试和验收结果。

## 2. Reconcile the Specifications

在设计改动前，核对上下文地图、架构、Roadmap 和测试策略是否一致：

- 若详细计划与架构冲突，先暴露冲突，不通过局部实现规避。
- 若任务范围缺失，区分可以直接处理的小型工作与需要补充 Roadmap 的实质变更。
- 若验收标准不可执行，应先把它改写为可观察、可测试的条件。
- 若文档与代码行为不一致，应判断是实现偏离规范，还是规范已经过期；不要默认其中任一方正确。

## 3. Design the Smallest Coherent Change

一个合格的变更计划应同时说明：

- 要修改的模块、文件和公开接口
- 必须保持不变的兼容行为
- 数据流、依赖方向和类型契约的影响
- 成功路径、失败路径、边界条件和空值行为
- 最小充分测试集合
- 迁移、回滚或环境兼容性风险

“最小”指不扩大任务范围；“完整”指不能省略让目标行为成立所必需的错误处理、类型或验证。

## 4. Implement Against Contracts

实现过程以已确认的契约为检查点：

- 模块只通过允许的依赖方向协作。
- 数据解析、变换和输出必须保持显式、确定且可诊断。
- 公共接口变化必须有明确授权、调用方分析和迁移说明。
- 不用占位实现伪装完成，不用放宽验证或吞掉异常制造通过状态。
- 发现超出当前任务的缺陷时，记录其影响；除非它阻塞当前验收，不顺带扩展修改范围。

## 5. Build an Evidence Chain

验证不是命令清单，而是从需求到证据的映射：

1. 每项验收条件对应至少一种可观察证据。
2. 测试层级与风险层级匹配：局部逻辑用单元测试，模块协作用集成测试，关键用户或数据流程用端到端测试。
3. 缺陷修复包含能在修复前失败的回归场景。
4. 数据与 schema 变更验证契约、泄漏边界、确定性和错误输入。
5. 环境失败与实现失败分开记录；未执行的验证不计为通过。

优先运行与变更直接相关的最小充分验证，再根据影响范围扩大验证。所有结果都应记录实际命令、退出状态和必要诊断。

## 6. Close the Loop

任务结束时，依次判断：

- 目标行为与验收标准是否全部满足
- 是否存在未验证部分或真实剩余风险
- 架构或公共契约是否变化
- Roadmap 状态、范围或完成记录是否变化
- 标准测试命令、矩阵或基线是否变化
- 当前焦点或项目入口是否变化
- 是否产生了可跨任务复用且尚未被规范覆盖的经验

只更新事实真正归属的文档。不要为了形式完整而在多个文件重复写入同一结论。

## Lessons Qualification

一条经验只有同时满足以下条件，才适合进入 `LESSONS.md`：

- 能跨任务复用
- 能表达为明确行动规则
- 不是一次性故障或状态日志
- 尚未被架构、测试或工作流规则覆盖

推荐表达：

> 当 `<条件>` 时，应 `<行动>`，因为 `<原因>`。

当经验成熟为稳定边界或质量门槛时，应迁移到 `ARCHITECTURE.md` 或 `TESTS.md`，并从 `LESSONS.md` 移除或标记为已取代。

## Reporting Principle

最终报告应让读者无需查看过程日志，也能区分：完成了什么、改了什么、实际验证了什么、尚有哪些风险，以及哪些项目文档需要更新。报告的可信度来自可追溯证据，不来自肯定措辞。
